## Implementation decisions

### Separate compatibility families

The existing PHP builder uses Buildx local exports and branches for historical
differences. Python follows the same pattern. The initial modern branch is
`feat/python-modern-wasm`; the site branch is `feat/python-wasm-playground`.
Historical configure scripts, host tools, and Emscripten workarounds belong in
separate family recipes/branches, sharing the runtime artifact contract.

### A native compiler process produces a Wasm interpreter

Modern CPython needs a native Python built from the same source to generate
frozen modules and other build assets. That native binary is not distributed.
The second compiler is Emscripten; exported `python.wasm` must have the actual
WebAssembly magic bytes and execute successfully in Node.

### Package source rather than incompatible bytecode

Each runtime receives its own standard library. The modern recipe creates a
sorted, timestamp-normalized ZIP of Python source with fixed file permissions,
then preloads it into MEMFS. It never packages `.pyc` files generated by a
different host interpreter. Tests, desktop GUI files, ensurepip, and venv are
excluded from this initial browser profile.

### Keep compiler configuration probes separate from filesystem packaging

The first modern configure attempt failed because `emconfigure` uses
`NODERAWFS` for compiler probes, while `--preload-file` requires the virtual
filesystem. The correction passes packaging flags only to the final `make`
link step. This was an actual failed build, followed by a corrected attempt;
it is not a runtime limitation.

### A worker per execution

The playground starts a fresh module worker for each run. This makes Stop and
timeout effective even when Python is in an infinite loop. No pthreads or
SharedArrayBuffer are needed for this execution model, so it fits ordinary
GitHub Pages hosting. It is one-shot execution: interpreter variables and
MEMFS files do not persist between runs.

### Explicit trampoline dependency in static modern builds

The first 3.15 Wasm binary linked successfully but failed during loader startup:
`ReferenceError: addFunction is not defined` in `getPyEMTrampolinePtr`.
CPython's modern Wasm-GC call trampoline adds a function to the indirect table.
The usual upstream dynamically linked profile retains the helper; this static
profile must include `$addFunction` explicitly and permit table growth. The
corrected final link is under test. Build stages now separate configuration,
object compilation, linking, and execution checks so linker corrections do not
force recompilation of every CPython object.

### Optional package loading is a runtime capability

The Pyodide adapter offers explicit switches for micropip and loading supported
packages detected in imports. Bare CPython builds disable those controls.
They do not gain a package manager, browser Fetch integration, or compatible
extension wheels merely by including the same Python standard library.

### Evidence travels with the build

Every modern export includes `smoke.json` and `manifest.json`, alongside
`python.mjs`, `python.wasm`, `python.data`, and the CPython license. The manifest
records source URL/checksum, compiler identity, artifact hashes, measured import
capabilities, and the Node result. Browser acceptance remains a separate result.
The site export script verifies hashes and the observed Python version before
adding a runtime to the selectable catalog.
